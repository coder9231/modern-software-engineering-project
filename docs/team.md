# 团队与分工

成员、负责人、交流渠道和课程截止时间尚待团队填写。以下是待认领职责与建议协作节奏，不是已经完成的人员分配或仓库配置；具体任务以 Issue 的认领与验收条件为准。

## 待认领职责

| 职责           | 主要交付物                                      | 认领人 | 备份评审人 |
| -------------- | ----------------------------------------------- | ------ | ---------- |
| 迭代协调与需求 | 整理需求优先级、Issue 范围、演示与周复盘        | 待认领 | 待认领     |
| 共享算法与 CLI | 统计/数学规则、JSDoc 契约、边界测试、命令行输出 | 待认领 | 待认领     |
| Web 与交互     | 页面、Worker 接口、取消/超时、响应式与辅助设置  | 待认领 | 待认领     |
| OCR 与数据边界 | 本机资源、人工校正、可选 AI 配置与真实样本验证  | 待认领 | 待认领     |
| 质量与交付     | CI、覆盖率、E2E、性能测量、Docker 实跑记录      | 待认领 | 待认领     |
| 文档与课程联系 | 使用指南、设计决策、需求追踪与个人贡献证据      | 待认领 | 待认领     |

一人可以认领多项职责；建议算法或接口修改至少由另一人复核，负责人不应代替其他成员的实际贡献记录。

## 每周建议节奏

| 时间         | 建议活动                                               | 留下的证据                       |
| ------------ | ------------------------------------------------------ | -------------------------------- |
| 周初 20 分钟 | 选本周目标，拆成能独立验收的 Issue，明确负责人和评审人 | Issue 的范围、完成条件与关联依赖 |
| 周中异步     | 小 PR、复现失败、及时同步阻塞；必要时 10 分钟讨论      | PR、最小复现、实际检查结果       |
| 周末 30 分钟 | 按老师/学生真实操作演示，检查回归与待验收项            | 对应提交、演示结果、剩余问题     |
| 周末 15 分钟 | 复盘一次做得好和一次需改进的实践，确定下一步           | 简短复盘及下一周 Issue           |

具体日期、会议地点、沟通渠道、迭代周期与课程截止时间均待团队确认。可建议使用待办→进行中→评审中→完成的看板，但本仓库文档不表示 GitHub Projects 已经创建。

## 认领与评审

认领时写明预计范围、验收样例和依赖；遇到问题及时更新 Issue，避免长时间无人知晓。评审重点为功能正确、边界明确、包依赖单向、隐私表述一致、文档可照做，以及验证证据对应当前改动。完整标准见[贡献指南](../CONTRIBUTING.md)。

完成的定义：验收条件满足；相关检查通过或明确记录未验证原因；文档和契约同步；需要评审的改动已评审。代码量只能观察规模，不能直接代表个人贡献或工程质量。记录个人贡献时引用 Issue、PR、设计讨论和测试工作。

## 仓库与站点权限

源码仓库为 [coder9231/modern-software-engineering-project](https://github.com/coder9231/modern-software-engineering-project)。可读取仓库的成员是否有直接写入权限，须由仓库管理者核对；外部贡献可按仓库实际可见性和权限采用 Fork/PR 流程。协作者邀请、分支保护、必需检查与审批人数需管理者实际配置后再记录为已启用。

[现有线上站点](https://se-practice-coder9231.a0910663736.chatgpt.site)与 GitHub 权限分别管理。当前迭代保留线上站点，只交付 CI 与 Docker；团队应在发布安排明确后单独记录版本、环境、负责人、检查与回滚方案，不能把 PR 合并视为自动发布。
